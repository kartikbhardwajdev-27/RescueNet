# Deploying RescueNet to Vercel with MongoDB Atlas

This puts RescueNet on the internet: the app on **Vercel**, the data in **MongoDB Atlas**. The
laptop mode (local MongoDB, `npm run start:lan`) keeps working exactly as before; nothing here
changes it. Do the steps in order. Dashboards change their wording now and then, so if a button is
named a little differently, look for the same idea.

You do this by hand: it needs your accounts. Nothing in the repo creates accounts or deploys.

Words used below: **cluster** = the database server Atlas runs for you; **connection string** = the
address and password the app uses to reach it; **env var** = a setting the app reads when it starts.

---

## 0. What you need

- A GitHub account that can see the `RescueNet` repository, with the `rebuild` branch pushed.
- A free MongoDB Atlas account and a free Vercel account.
- A terminal with `openssl` (every Mac has it) to make the secret.

## 1. MongoDB Atlas

### 1.1 A NEW cluster

1. Sign in at <https://cloud.mongodb.com>. Pick (or create) an organization and a **new project**
   (Projects, **New Project**, name it `rescuenet`).
2. **Create** a cluster (Database, **Build a Database** or **Create**). Choose the free **M0** tier.
3. Provider **AWS**. Region: **Mumbai (ap-south-1)**, the closest to Chandigarh. Name it
   `rescuenet`. Create it, and wait a few minutes until it says it is ready.

> Do not reuse an older cluster or project. An old `.env` with an Atlas address and password was
> committed to the public repo on the `master` branch by a teammate (see `docs/SECURITY.md`).
> Treat that cluster as exposed: use a new one, and delete the old cluster or at least its old
> database user.

### 1.2 A NEW database user

1. Left menu, **Security**, **Database Access**, **Add New Database User**.
2. Authentication method **Password**. Username: `rescuenet-app` (not any name you used before).
3. Click **Autogenerate Secure Password** and **copy it now** into a safe place; you cannot read it
   again later (you can only reset it).
4. Under **Database User Privileges** choose **Specific Privileges**, add the role `readWrite` on
   the database `rescuenet` (collection left empty). That user can then touch only that database.
5. **Add User**.

### 1.3 Network access

1. Left menu, **Security**, **Network Access**, **Add IP Address**.
2. Vercel's servers have no fixed address, so choose **Allow Access From Anywhere**
   (`0.0.0.0/0`). The database is still protected by the user name and password, so keep that
   password long and secret. (To restrict it you need a paid Vercel feature for fixed addresses.)
3. **Confirm**, and wait until the status says Active.

### 1.4 The connection string

1. **Database** (left menu), your cluster, **Connect**, **Drivers**.
2. Driver **Node.js**. Copy the string. It looks like
   `mongodb+srv://rescuenet-app:<db_password>@rescuenet.xxxxx.mongodb.net/?retryWrites=true&w=majority`
3. Edit it before you use it:
   - replace `<db_password>` with the password from step 1.2. If the password contains characters
     like `@ : / ? # %`, encode them (for example `@` becomes `%40`). An autogenerated password
     usually has none.
   - put the database name after the `/`, so it ends `.mongodb.net/rescuenet?retryWrites=...`.
     Without a name the app would use a database called `test`.
4. Keep this edited string private. It is the value of `MONGODB_URI` below. Never paste it into
   chat, a commit, or a screenshot.

## 2. The secret for login

In a terminal:

```sh
openssl rand -hex 32
```

It prints 64 characters. That is `JWT_SECRET`. The server refuses anything shorter than 32. Use a
new one for the hosted site; do not reuse your laptop's.

## 3. Vercel

1. Sign in at <https://vercel.com> (use **Continue with GitHub**).
2. **Add New**, **Project**, find `RescueNet`, **Import**. (If it is not listed, **Adjust GitHub App
   Permissions** and allow that repository.)
3. On the configure page:
   - **Framework Preset**: Next.js (detected).
   - **Root Directory**: click **Edit** and choose **`app`** (the Next.js app is in that folder,
     not at the repo root). Leave "Include source files outside of the Root Directory" as it is.
   - **Build Command / Output Directory / Install Command**: leave the defaults.
   - **Environment Variables**: add these two (type each name, paste each value, **Add**):
     - `MONGODB_URI` = the edited connection string from step 1.4
     - `JWT_SECRET` = the 64 characters from step 2
     Leave both ticked for **Production** (and Preview, if you want preview deployments to work).
4. **Do not click Deploy yet.** First set the production branch (next step), then deploy.
   (If you already did, that is fine: change the branch below and redeploy.)

### 3.1 Production branch

The code is on the `rebuild` branch, not `main`.

1. Open the project, **Settings**, **Environments** (older dashboards: **Git**).
2. **Production**, **Branch Tracking**, set the production branch to **`rebuild`**. Save.
3. **Deployments**, find the latest deployment of `rebuild`, **...**, **Redeploy** if needed.

### 3.2 Check the project settings

- **Settings, Functions** (optional): set the Function Region to **Mumbai (bom1)** to sit next to
  the database. Redeploy after changing it.
- **Settings, Deployment Protection**: make sure **Vercel Authentication** is **off** for
  Production. If it is on, a phone sees a Vercel login page instead of RescueNet, and the Android
  app gets answers that are not from RescueNet.
- You do **not** need to set `COOKIE_SECURE`: Vercel serves https and the app marks the login
  cookie Secure by itself. You do **not** need `RATE_LIMIT_STORE`: with a database that is not on
  the same machine, the app keeps its rate limits in MongoDB by itself.

The first build takes a few minutes. When it finishes you get an address like
`https://rescuenet-xxxx.vercel.app` (the production domain is shown on the project's overview).

## 4. Check it works (post-deploy checks)

Replace `https://YOUR-SITE` with your address. All of these should work on your phone too.

1. **Health.** Open `https://YOUR-SITE/api/health`. It must show
   `{"status":"ok","db":"connected"}`. If `db` says `disconnected`, the connection string or the
   Atlas network access is wrong (see Troubleshooting).
2. **Register.** Open `/register`, make a citizen account. You should land logged in. Reload the
   page: still logged in (the Secure cookie works over https).
3. **SOS.** Press the red SOS button, allow location, send. It says it was sent. Open **Home**: the
   alert shows in Recent activity. (This writes a real record into Atlas: it is a test, resolve it
   or leave it.)
4. **Map.** Open `/map`. You should see the map and the demo or real markers. In the browser's
   developer tools, Network tab, `tricity.pmtiles` requests answer **206 Partial Content** (not
   200 with the whole file).
5. **Install.** On a phone, open the site in Chrome: the menu has **Install app** / **Add to Home
   screen**. The full phone test is section 17 of `docs/TEST_CHECKLIST.md`.
6. **Rate limit.** Press SOS 11 times quickly, or send 11 wrong logins: the 11th is refused with
   "Too many requests". Two different phones on the same WiFi share one address and one count.

Logs: Vercel project, **Logs** (runtime logs). A line `[rescuenet] Missing environment variables:
MONGODB_URI` or `... JWT_SECRET is shorter than 32 characters` means a setting is wrong; it
names the variable and never prints a value.

## 5. Demo data (optional)

An empty site has no shelters. To add the six demo shelters, two demo accounts, demo incidents and
events to the hosted database, from your laptop, in `app/`:

```sh
cd app
MONGODB_URI='<the edited connection string>' DEMO_PASSWORD='<a password of your own, 12+ characters>' \
  npm run demo:seed:hosted -- --hosted
```

It shows the host and database name and asks you to type the database name before it writes
anything. It refuses a missing, short, common or default `DEMO_PASSWORD`, refuses a local
database, only adds records marked as demo, and deletes nothing. The two demo accounts
(`demo.citizen@rescuenet.test`, `demo.org@rescuenet.test`) use that password: anyone who knows it
can log in as them, so use it for a demo and remove the accounts afterwards (from Atlas, **Browse
Collections**, `users`, filter `{ "seeded": true }`).

Type the command with a leading space if your shell keeps history of passwords (zsh with
`HIST_IGNORE_SPACE`), or put the values in the current shell with `export` and close it afterwards.

## 6. The Android app pointed at the hosted site

```sh
cd app
RESCUENET_SERVER_URL=https://YOUR-SITE npm run apk
```

The first screen of the app then starts with that address filled in (it is still editable on the
Settings page, and an address you save wins). Only `https://` is accepted for a public address;
`http://` is only for addresses on your own network. The APK is built in `app/dist/RescueNet.apk`.
See `docs/APK_SETUP.md` for installing it.

## 7. What changes between the laptop and the hosted site

| | Laptop (`npm run start:lan`) | Hosted (Vercel + Atlas) |
|---|---|---|
| Database | MongoDB on the laptop | Atlas |
| Rate limits | In memory (reset on restart) | In MongoDB, shared by all instances |
| Client address for limits | Last `x-forwarded-for` entry | `x-vercel-forwarded-for` (set by Vercel) |
| Login cookie | Not Secure (plain http works) | Secure (https) |
| Works with no internet | Yes (the laptop is the server) | No: the app shell, the map and the saved data work offline once opened, reports queue |

### The client-address caveat (spoofing)

The per-address rate limits trust a header that says who the caller is. On Vercel, the app reads
`x-vercel-forwarded-for`, which Vercel sets itself and a caller cannot forge. Anywhere else (the
laptop, or any other host) the app reads the **last** `x-forwarded-for` entry, which is only
trustworthy when a reverse proxy you control is in front and appends it; with no proxy in front, a
caller can invent that header and pick a new "address" for every request, defeating the
per-address limits. The per-account login limit counts by e-mail instead and still holds. Do not
put another proxy or CDN in front of Vercel without checking how it forwards the address. Limits
are a brake on abuse, not a security boundary.

If the database cannot be reached while a request is being counted, the limiter lets that request
through (and logs it), because the request would fail on the database anyway.

## Troubleshooting

- **`/api/health` shows `"db":"disconnected"`**: Atlas Network Access has no `0.0.0.0/0` entry (or
  it is not Active yet), the password in `MONGODB_URI` is wrong or not URL-encoded, or the user has
  no role on the `rescuenet` database. Fix it in Atlas, then **Redeploy** in Vercel (env var changes
  apply only to new deployments).
- **Build fails**: open the deployment, **Build Logs**. Confirm **Root Directory** is `app`.
- **Every API call says Unauthorized / you see a Vercel login page**: Deployment Protection (above).
- **Login works but you are logged out on the next page**: the site was opened over plain `http://`
  by mistake; use the `https://` address.
- **The map is blank**: `tricity.pmtiles` must be deployed (it is committed, about 3.7 MB). Check
  `/maps/tricity.pmtiles` answers 206 to a range request.
- **Changed a setting in Vercel and nothing changed**: settings apply to the next deployment.
  **Deployments, ..., Redeploy**.
